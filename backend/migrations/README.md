# Go 数据库迁移策略

`backend/migrations/` 是当前数据库结构的唯一迁移来源。首次生产发布前的开发迁移已收敛为四个最终态分组：

| 版本 | 分组 | 内容 |
|------|------|------|
| `0001_initial_schema` | 基础结构 | 身份、班级、内容、学习、DKT、AI 配置和安全 |
| `0002_student_ai_safety` | AI 风控 | 学生访问控制、用量统计和模型审核 |
| `0003_communication` | 站内通信 | 公告、私信、通知、答疑、快照触发器和附件 |
| `0004_delivery_integrations` | 外部通知 | 微信绑定与提醒任务、邮件模板 |

这四个文件只描述空库的最终结构，不包含开发期的重命名、先建后删、历史回填或旧实例兼容逻辑。首次生产部署后，它们即视为已发布历史。

## 基线兼容边界

- 全新数据库应从版本 `0001` 顺序执行到 `0004`。
- 执行过旧开发迁移链 `0001` 至 `0015` 的临时数据库必须删除并重建；migration runner 只按版本号判断已应用状态，不能在旧记录上直接运行新基线。
- 对不可丢弃的数据库，不得删除 `go_schema_migrations` 记录后重放。应停止发布并单独设计、评审和验证数据保留迁移。
- 从首次生产发布开始，所有结构或数据变化从 `0005` 起追加，不再重写 `0001` 至 `0004`。

## 新增迁移

- 文件名使用 `NNNN_description.up.sql`，版本号连续且一经发布不可复用。
- 不修改 `0001` 至 `0004` 承载增量变化，也不重建已经发布的迁移历史。
- 每个迁移保持单一目的，明确约束、索引、默认值和数据修正的执行顺序。
- 结构或数据变更必须经过评审；禁止在没有迁移记录的情况下直接修改共享数据库。

## 执行与验证

在 `backend/` 目录运行：

```powershell
go run ./cmd/migrate
go run ./cmd/migrate
```

全新空库首次执行当前基线应为 `applied_count=4`，紧接着重复执行应为 `applied_count=0`。后续版本首次执行记录实际待应用数量，重复执行仍必须为 `0`。发布前还应在一次性空库验证关键表、约束、索引、默认值和种子数据。

## 发布与回滚

- 生产迁移前先创建并验证可恢复备份，迁移成功后再启动依赖新结构的 API 版本。
- migration runner 不由 API 自动执行，部署流程必须显式运行。
- 不提供自动 down migration；失败时恢复备份，或发布经过评审的补偿性 forward migration。
- 回滚应用镜像前，先确认旧版本能够读取迁移后的结构。
- 仓库外数据库若执行过未发布、旧开发链或不同内容的同版本迁移，先核对实际 schema 和 `go_schema_migrations`，不得通过删除版本记录盲目重放。

历史 Alembic 链已退出当前工作区；需要追溯时使用 Git 历史或已归档的发布材料。
