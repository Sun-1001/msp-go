# Go 数据库迁移策略

`backend/migrations/` 是当前数据库结构的唯一迁移来源。首次生产发布前的开发迁移已收敛为四个最终态基线分组，随后由每日一题迁移扩展：

| 版本 | 分组 | 内容 |
|------|------|------|
| `0001_initial_schema` | 基础结构 | 身份、班级、内容、学习、DKT、AI 配置和安全 |
| `0002_student_ai_safety` | AI 风控 | 学生访问控制、用量统计和模型审核 |
| `0003_communication` | 站内通信 | 公告、私信、通知、答疑、快照触发器和附件 |
| `0004_delivery_integrations` | 外部通知 | 微信绑定与提醒任务、邮件模板 |
| `0005_daily_question` | 每日一题 | 固定日题、班级策略、题目日程、公众号提醒和统计 |

`0001` 至 `0004` 是空库基线，`0005` 是每日一题的唯一新增迁移。

## 基线兼容边界

- 全新数据库按 `0001` 至 `0005` 执行，首次记录版本 `1` 至 `5`。
- migration runner 会同时校验版本号和迁移名称，并拒绝应用记录与当前代码不一致或包含未知版本的数据库。
- 执行过旧开发迁移链 `0001` 至 `0015` 的临时数据库必须删除并重建，不能通过修改 `go_schema_migrations` 记录使其伪装为当前基线。
- 对不可丢弃的旧数据库，应停止发布并单独设计、评审和验证数据保留迁移。
- 后续结构或数据变化从 `0006` 起追加，不再重写已发布的 `0001` 至 `0005`。

## 新增迁移

- 文件名使用 `NNNN_description.up.sql`，版本号连续且一经发布不可复用。
- 不修改已发布的 `0001` 至 `0005` 承载增量变化，也不重建已经发布的迁移历史。
- 每个迁移保持单一目的，明确约束、索引、默认值和数据修正的执行顺序。
- 结构或数据变更必须经过评审；禁止在没有迁移记录的情况下直接修改共享数据库。

## 执行与验证

在 `backend/` 目录运行：

```powershell
go run ./cmd/migrate
go run ./cmd/migrate
```

全新空库首次执行应记录当前全部嵌入版本，紧接着重复执行应为 `applied_count=0`。后续版本首次执行记录实际待应用数量，重复执行仍必须为 `0`。发布前还应在一次性空库验证关键表、约束、索引、默认值和种子数据。

## 发布与回滚

- 生产迁移前先创建并验证可恢复备份，迁移成功后再启动依赖新结构的 API 版本。
- migration runner 不由 API 自动执行，部署流程必须显式运行。
- 不提供自动 down migration；失败时恢复备份，或发布经过评审的补偿性 forward migration。
- 回滚应用镜像前，先确认旧版本能够读取迁移后的结构。
- 仓库外数据库若执行过未发布、旧开发链或不同内容的同版本迁移，先核对实际 schema 和 `go_schema_migrations`，不得通过删除版本记录盲目重放。

历史 Alembic 链已退出当前工作区；需要追溯时使用 Git 历史或已归档的发布材料。
